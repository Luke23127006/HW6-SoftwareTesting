# HW06 Test Environment

## Backend lifecycle

- Install: run `npm install` in `eshop-sut/backend/`.
- Initialize/reset data: run `node database.js` in `eshop-sut/backend/`.
- Start: run `node server.js` in `eshop-sut/backend/`.
- Base URL and port: `http://localhost:3000`.
- `server.js` imports `database.js`; because `database.js` calls `initDatabase()` at module load, every backend start drops and recreates the core tables and reseeds users, coupons, products, and categories. State does not persist across backend restarts.

## Seed fixtures

- Admin: `admin@eshop.com` / `Admin123!`, role `admin`.
- Normal user: `test@eshop.com` / `Test1234!`, role `user`.
- Coupons: `SAVE10`, `BIGBUY`, `VIP100`, and `EXPIRED`.
- Numeric IDs are generated by SQLite. Tests should capture returned IDs or query/create runtime data instead of assuming stable IDs.

The setup guide separately lists `admin123` for the admin password, which conflicts with the database seed `Admin123!`. Treat this as an environment-documentation ambiguity; verify against the initialized database during execution.

## Selected endpoint setup and isolation

### `POST /api/login`

- Uses a seeded or runtime-created user.
- Mutates `users.login_attempts` and `users.locked_until`; login state tests can interfere when sharing one account.
- A successful login resets both fields. Restarting the backend also resets all database state.
- The implementation returns a JWT and a `user` object on success. This observation is not a substitute for the specification's expected contract.

### `POST /api/apply-coupon`

- Uses coupon rows and optionally `coupon_usage` rows associated with `user_id`.
- The route itself does not record usage; `POST /api/coupon-usage` records usage and requires a bearer token.
- Usage-limit tests can interfere through shared `coupon_usage` rows. Prefer fresh runtime users/coupons or reset the backend between stateful groups.
- The selected route is implemented without authentication middleware even though FR-09 includes authentication requirements. Preserve the requirement as the oracle and treat runtime behavior only as an observation.

### `POST /api/admin/coupons`

- Requires a syntactically valid bearer token through `authenticateToken`.
- The implementation does not visibly enforce the decoded role at this route; authorization expectations must remain traceable to FR-17/security requirements.
- Coupon `code` is unique at the database layer. Use unique runtime codes and capture the returned `id`.
- Cleanup is available through `DELETE /api/admin/coupons/:id`, also guarded by token authentication. Delete only coupons created by the test.

## Execution cautions

- Run stateful cases serially unless each case owns isolated data.
- Start from a known database reset for reproducibility.
- Do not run `node database.js` while the server is active because both modules open the same SQLite file and initialization is destructive.
- Expected values absent from the supplied requirements/specification remain `SPEC_UNDEFINED`; implementation details above are test setup observations only.
